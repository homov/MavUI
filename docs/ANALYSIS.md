# Анализ проекта Md3.Avalonia: утечки, производительность, код, дубли

Дата: 2026-10-22. Метод: статический анализ исходников (поиск паттернов, подсчёт
подписок на события, анализ кода в `Render`/`OnRender`, поиск повторяющихся блоков).
Профилирование и замеры не проводились. Все пункты ниже — гипотезы, которые нужно

Обозначения приоритета: **H** — высокий, **M** — средний, **L** — низкий.

## 1. Утечки памяти

Большинство очевидных случаев уже обработано: списки оверлеев и
`MdKeyboardAvoidingHost` очищаются, `MdTheme.Observe` держит view через
`WeakReference`, `MdMotion` проверяет владельца анимации, `MdDataTable` считает
подписки на элементы строк.

| # | Место | Описание | Приоритет |
|---|---|---|---|
| 1.1 | `Theming/MdTheme.cs`, `Observe` (67 вызовов `Observe(this, ...)`) | Статическое событие `MdTheme.Changed` удерживает обработчик, пока view подписан. **Замер (раздел 0): после закрытия подписки = 0, объекты освобождены.** Риск остаётся только при detach, который не пришёл. | L |
| 1.2 | Дочерние `PropertyChanged += (_, e) => ...` (`MdTextField`, `MdSearchBar`, `MdTimePicker` и др.) | Подписки на собственные дочерние контролы. Не утечка, но замыкание держит родителя, пока жив ребёнок. | L |
| 1.3 | `Controls/MdDataTable.cs:804` | Ручной подсчёт ссылок на `PropertyChanged` элементов строк. Логика корректна, но хрупка. Тест «добавить/удалить строку N раз → 0 подписок» ещё не написан. | M |

## 0. Базовая линия (замер, Tests/LifecycleBenchmarks.cs)

Источник: `ci/benchmark-lifecycle.txt`, `ci/benchmark-theme.txt` (run `39808...`, Headless, Release).

| Метрика | Значение |
|---|---|
| Контролов (MdButton, MdCard, MdTextField, MdSlider) | 500 |
| Подписчиков `MdTheme.Changed` до / при показе / после закрытия | 0 / 1125 / 0 |
| Контролов живых после закрытия и 3× `GC.Collect` | 0 |
| Смена темы (Dark↔Light) при 500 подключённых контролах | медиана 42.8 ms (диапазон 38–64 ms, 6 замеров) |

Выводы:
- **Утечки подписок и памяти в этом сценарии не подтверждены** (пункты 1.1 и 1.3 снижены до L: проверено, что после закрытия подписки и объекты освобождаются).
- **Смена темы ~43 ms** — заметна (это около 2–3 кадров при 60 FPS). Это новая точка для оптимизации: профилировать `MdTheme.Changed` → `apply` каждого контрола.
- Ограничения: Headless-рендер без реального GPU, 6 замеров, один прогон. Цифры — ориентир для сравнения, а не абсолютная производительность на устройстве.

## 2. Производительность

| # | Место | Описание | Приоритет |
|---|---|---|---|
| 2.1 | `Platform/MdTextMetrics.cs`, `FormattedTextCache` | В ключ входит `maxTextWidth` (double). При ресайзе окна каждая новая ширина создаёт новую запись. Обрезка идёт по порядку обхода словаря, а не по давности, поэтому при анимациях возможен thrashing. Решение: LRU или округление ширины до шага (например, 4 px) в ключе. | M |
| 2.2 | `Theming/MdTheme.cs`, `TrimCache` | Та же схема обрезки (первые N ключей), что и в 2.1. | M |
| 2.3 | `Controls/MdDataViz.cs:371`, `RenderLine` | `vals.Min()`, `vals.Max()` и аллокация `Point[]` на каждый рендер. Однопроходный расчёт дешевле. | L |
| 2.4 | Layout (`MeasureOverride`/`ArrangeOverride`, 29 файлов) | Явных O(N²) циклов не найдено. Нужно профилирование `MdList`, `MdDataTable`, `MdTreeView`. Базовая линия — `Tests/VirtualizationBenchmarks.cs`. | M |
| 2.5 | `Controls/MdIcons.cs` (10 863 строки) | Если это большая статическая таблица, построенная при старте, она увеличивает время запуска. Нужно проверить, строится ли она лениво. | M |

**Поправка к предварительному анализу.** Ранее предлагалось кэшировать геометрию
в `MdProgress.Render` (`MdLoadingIndicator`). Это неверно: форма зависит от
`_phase`, которая меняется каждый кадр, поэтому кэш не даст попаданий. Остаются
только мелкие аллокации (массив из 14 точек). Пункт снят с приоритета.
